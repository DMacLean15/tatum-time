================================================================
  SEND THE NEWSLETTER FOR REAL  (optional, ~15 min one time)
================================================================

Right now the site COLLECTS subscribers (they're saved in Supabase),
but nothing ever emails them. This turns on real sending: after Dan
publishes a post, he opens one link, clicks "Send now", and every
subscriber gets a clean Celtics-green email about the new post.

Until this is set up, nothing changes - the sender page just says
"not configured yet". Safe to skip or do later.

WHAT YOU NEED
  1. A free account at https://resend.com  (the email service; the
     free tier sends 100 emails/day - plenty).
  2. Your Supabase project's "service_role" key:
     Supabase → Project Settings → API keys → service_role (secret).
     NEVER put this key in the website code - it only goes in
     Cloudflare's env vars (below), which stay server-side.

STEP 1 - VERIFY THE DOMAIN IN RESEND  (so emails come from tatumtime.net)
  Resend → Domains → Add Domain → tatumtime.net → it shows a few DNS
  records → add them in Cloudflare DNS → wait for "Verified".
  Then create an API key: Resend → API Keys → Create.

STEP 2 - ADD 4 ENV VARS IN CLOUDFLARE PAGES
  Cloudflare → your Pages project → Settings → Environment variables
  (add to "Production"):

    NEWSLETTER_KEY        = any long random secret, e.g. from
                            https://www.random.org/strings/
                            (this becomes the ?key= in Dan's link)
    SUPABASE_SERVICE_KEY  = the service_role key from Supabase
    RESEND_API_KEY        = the API key from Resend
    NEWSLETTER_FROM       = Tatum Time <posts@tatumtime.net>

  Then redeploy the site once (Deployments → Retry deployment) so the
  function picks the variables up.

STEP 3 - GIVE DAN HIS LINK
  Bookmark this for him:

    https://tatumtime.net/send-newsletter?key=THE-SECRET-FROM-STEP-2

  His routine after publishing a post:
    1. Wait for the deploy to finish (post shows on the site).
    2. Open the bookmark → he sees a preview + subscriber count.
    3. Click "Send now →". Done.

  Notes:
    - Every subscriber gets an individual email; addresses are
      never visible to each other.
    - It always sends the NEWEST published post.
    - Each post can only be sent ONCE. Opening or refreshing the
      link never sends; only the "Send now" button does, and after
      that the page says "already sent on <date>".
    - Only CONFIRMED subscribers get it (see the upgrade below), and
      every email has its own unsubscribe link.


================================================================
  UPGRADE - run once  (double opt-in, unsubscribe, send-once log)
================================================================

What changed:
  - Signing up on the homepage now goes through /api/subscribe.
    The person gets a "Confirm your subscription" email and is only
    added to the newsletter after clicking the link (/api/confirm).
  - Every newsletter email has an unsubscribe link (/api/unsubscribe)
    plus the one-click unsubscribe headers Gmail/Yahoo/Apple use.
    Unsubscribing keeps the row but stamps unsubscribed_at, so that
    address is never mailed again unless they sign up + confirm again.
  - Each post is logged in a new newsletter_sends table BEFORE it is
    mailed, so the same post can never go out twice.
  - People who signed up with the old form are kept and counted as
    confirmed (they opted in already).

ORDER MATTERS:
  1. FIRST add the env vars from STEP 2 above (SUPABASE_SERVICE_KEY,
     RESEND_API_KEY, NEWSLETTER_FROM, NEWSLETTER_KEY), verify the
     domain in Resend (STEP 1), and redeploy. Signups go through the
     server from now on, so they need those keys.
  2. THEN run this SQL. It removes the old "anyone can add an email"
     rule, so after this the homepage form only works through
     /api/subscribe. Safe to run twice.

  Supabase -> SQL Editor -> New query -> paste + Run:

-------------------- copy from here --------------------
alter table subscribers add column if not exists confirmed       boolean not null default false;
alter table subscribers add column if not exists token           text;
alter table subscribers add column if not exists confirm_sent_at timestamptz;
alter table subscribers add column if not exists unsubscribed_at timestamptz;
create unique index if not exists subscribers_token_key on subscribers (token);

-- only the server (service key) may add or change subscribers now
alter table subscribers enable row level security;
drop policy if exists "public can subscribe" on subscribers;

-- tidy old addresses to lower case (the server always saves lower case);
-- skips any that would clash with an existing lower-case copy
update subscribers s set email = lower(trim(s.email))
 where s.email <> lower(trim(s.email))
   and not exists (select 1 from subscribers d where d.email = lower(trim(s.email)));

-- grandfather everyone who signed up with the old form (new signups
-- always get a token from the server, so a second run changes nothing)
update subscribers
   set confirmed = true, token = gen_random_uuid()::text
 where token is null;

-- one row per post that has been mailed
create table if not exists newsletter_sends (
  post_slug   text primary key,
  sent_at     timestamptz not null default now(),
  recipients  int
);
alter table newsletter_sends enable row level security;
-- (no policies on purpose: only the server's service key can read/write it)
--------------------- to here --------------------------

Check it worked: Supabase -> Table Editor -> subscribers shows the
new columns, old rows have confirmed = true and a token.

To re-send a post on purpose (rare): delete its row in
Table Editor -> newsletter_sends, then use the send link again.
